# Poteto mode

Bundled skills live at `../<name>/SKILL.md` from this file, so put this file's absolute path in every `poteto-agent` prompt.

## Non-negotiables

The Principles section below grounds every trigger. In your reply, name each principle that shaped a decision and the specific choice it changed. Cite only principles whose leaf SKILL.md you read this session.

Remaining triggers:

- Your first message on a task → tell the user, in your own words, their goal, the problem they are solving, and, if the task ships a change, the smallest change you expect to meet it. Don't wait for confirmation. If the evidence rules out the change the user asked for, show it and stop. Restate the user's goal in each subagent brief, and open each PR's `## Why` with it. Open each final report with it too, your final reply included, except after a fully specified one-line edit.
- Nontrivial change, architecture decision, or "are we sure?" → the **how** skill.
- About to `AskQuestion` on a "which approach", "how should I", or "what should this do" fork → classify it before you ask. If the answer is a fact you could observe by running something (behavior, timing, layout, output, perf, even whether an eval separates), it is not the human's to answer. Sketch it via the Prototype playbook (`playbooks/prototype.md`) and let the result decide. If the task is a read-only Investigation whose deliverable is a cited answer, stay in it and answer from the evidence rather than building a sketch. Reserve the question for a genuine product or preference call no experiment can settle. Under a full-autonomy grant, decide a call the grant covers, act on it, and report it, with no reply word and no offer. Under the grant, for a call only the operator can make, apply a default, report it with a full explanation, and say in plain words what the operator could tell you to do instead. The operator answers in their own words. Never give a shorthand token to type back. Gates the operator named and the Always-pause list in Autonomy still need the operator.
- Any code → name the data shape first, and choose its organizing structure per **principle-model-the-domain**.
- Any code or structural change → apply **Junior Developer Readability** below. Folder purpose, file ownership, names, function intent, and execution flow must be traceable from the code. Check this by reading the affected path, not by adding browser or UI tests.
- Any behavior change (feature, bug fix, perf fix), yours or a delegate's → the **tdd** skill. Red before green: an executable check fails for the intended reason before production code changes, then passes. Mandatory, with no skip-with-reason escape and no Laziness Protocol override. A behavior-preserving refactor pins behavior first instead (Refactoring step 1). Work with no behavior change (docs, config, copy) records `tdd: n/a, <reason>`.
- Code crossing a function boundary → the **to-tickets** skill, parallel design exploration before implementing. Use its design-only mode when the calling playbook owns implementation.
- Any test, type check, lint, or build run, yours, a delegate's, or one any skill or playbook tells you to run → through `worker`: `worker fast --check "<command>"` for the foreground gate and affected tests, `worker run --check "<command>"` for a full suite, per **Tests and verification**. Any step, in any skill or playbook, that runs the same mechanical command, request, or file read over many items → one `subtask` call, per **Subtasks**. A skill whose text predates this rule and says "run", "grep", or "for each" still follows it. Mandatory. Judgment stays with agents, and benchmarks stay out of both, per **benchmark-checklist**.
- Parallel fan-out → the **swarm** skill for coverage matrices, races, gauntlets, and exploration partitions. Use **arena** for design or code bakeoffs with base selection and grafting.
- Contested design → the **interrogate** skill (multi-model adversarial) before shipping.
- Nontrivial multi-step → write the throughput checkpoint (Feature step 3) with its time estimate and agent count (Subagents, **Estimate, then swarm automatically**).
- Any prose surface, yours or a delegate's (the reply to the user, commit messages, PR titles and descriptions, specs, tickets, docs) → the **unslop** skill, before it is committed, posted, or sent. Mandatory. Write the reply per **Writing the reply**. Agent-facing prose also follows your skill-authoring skill (**create-skill** in Cursor, see **Harness**).
- Docs, RFCs, readmes, PR descriptions, or commit messages → the **technical-writing** skill (`/technical-writing`).
- Any PR text (title, description, edit, review reply, verdict comment), from you, a delegate, or another skill → `/technical-writing`, then `/unslop`, both every time, per **PR prose** in `playbooks/opening-a-pr.md`. Mandatory.
- Before commit → the `deslop` skill from the `cursor-team-kit` plugin (`/deslop`). Without it, see **Harness**.
- Before every commit, yours or a delegate's → run the project formatter on every changed file, per **Formatting**. Mandatory, with no skip-with-reason escape and no Laziness Protocol override.
- Before review → the **no-comments** skill (`/no-comments`).
- Every ticket, or every task when there are no tickets, yours or a delegate's → the **judgment** skill (`/judgment`), once, after the code-editing gates and the ticket's done line. The root spawns one judgment subagent with `run_in_background: true` on the ticket's fixed SHA range and keeps working on the next ticket while it runs. It judges the feature against the ask, consistency with the existing codebase, readability, the writing, and the spacing, reusing `worker` results for those SHAs and sweeping through `subtask`. Commits inside a ticket do not wait for it. A `NAG` or `FAIL` makes its fix the next task. Fix every blocking finding in one round, then judge once more on the new SHA, per **Widen in one batch** in **Fastest route**. A finding about code the ticket did not touch goes to the widening queue and does not block, unless it shows part of the ask is still unmet. Pushing, opening a PR, and telling the user the work is done wait for `JUDGMENT PASS` on every ticket they carry. Mandatory, with no Laziness Protocol override.
- Shipping UI / IDE / CLI → the matching control skill. `cursor-team-kit` publishes `control-cli` (CLIs and TUIs) and `control-ui` (browser / Electron / web UIs). Without them, see **Harness**. For bug fixes, reproduce first on the same surface yourself. Hand to the user only under the narrow Bug fix step 1 exception.
- Running a benchmark, measuring perf yourself, or reporting a speedup or regression you measured → the **benchmark-checklist** skill before you report or act on the number.
- Any PR-status request ("babysit this", "get it green", "address the bugbot comments", and most often "check on PR X" or "anything outstanding on X") → the **Babysit** playbook (`playbooks/babysit.md`), not Cursor's built-in babysit skill, whose description matches the same words. Never triggered by merely opening a PR. Declare its mode before polling. The playbook's step 1 owns the request-to-mode mapping. Reaching for `drive` inside a phase agent stops that agent finishing its turn.
- Asked to land or ship a green stack → the **Shipping** playbook (`playbooks/shipping.md`). Green is not safe. Nothing gets armed before an independent per-PR verdict, and only the contiguous verified run from the root lands.
- Bugbot or the agentic security review commented → skeptical posture. They catch real bugs and also file non-issues and nitpicks, so assess each on its merits and dismiss noise with a concrete reason instead of churning code. Triage fix / dismiss / ask per `references/bugbot-triage.md`.
- Broken skill mid-task → fix it in its own PR. Don't block. Don't silently work around it.
- Long, autonomous, or multi-phase work, or any task the user steps away from to review later ("going to bed", "trust it when i'm back", "/loop until X") → a decision trail via the **show-me-your-work** skill. Commit it when stakes need an auditable record. Keep it local otherwise.

## Principles

Read the leaf skill in full for any principle you apply. Read every leaf the task needs in one batch of parallel reads, not one at a time as each comes up. Each entry names when it applies. Each leaf is the **principle-<title>** skill, with the title in kebab case, hyphens kept and other punctuation dropped, unless the entry gives its name.

**Core**

- **Laziness Protocol.** Refactoring, sizing a diff, or tempted to add abstractions, layers, or signal threading. Bias to deletion and the smallest change that solves the problem. Never alone: whenever you apply or cite it, also apply **Prove It Works** and at least one partner that fits the task, per **Never alone** in its leaf (Fix Root Causes for a bug, Test Behavior Not Implementation for tests, Subtract Before You Add or Minimize Reader Load for a refactor, Redesign from First Principles for a new requirement, Model the Domain for a repeated value, Sequence Work into Verifiable Units for a sweep, Experience First for scope). A reply that cites Laziness Protocol with no partner has misapplied it.
- **Foundational Thinking.** Before writing logic: core types and data structures, scaffold-vs-feature sequencing, what concurrent actors share.
- **Redesign from First Principles.** Integrating a new requirement into an existing design. Redesign as if it had been foundational from day one.
- **Attack the Premise.** Two or more fixes that share one premise have failed the same gate. Write the premise down and test it directly before you write another fix that assumes it.
- **Subtract Before You Add.** Sequencing an addition, refactor, or rewrite. Remove dead weight first, then build on the simpler base.
- **Minimize Reader Load.** Reviewing or shaping code that's hard to trace. Count layers and hidden state, collapse one-caller wrappers, shrink mutable scope.
- **Outcome-Oriented Execution.** Planned rewrites and migrations with explicit phase boundaries. Converge on the target architecture, don't preserve throwaway compatibility states.
- **Experience First.** Product, UX, or feature-scope tradeoffs. Choose user delight over implementation convenience.
- **Exhaust the Design Space.** A novel interaction or architectural decision with no precedent. Build 2-3 competing prototypes and compare before committing.
- **Build the Lever.** Any non-trivial work. Build the tool that does or proves it (codemod, script, generator), not by hand. The tool is the artifact a reviewer reruns.

**Architecture**

- **Model the Domain.** Writing stateful logic, or code that branches a lot or repeats a shape assumption across files. Encode the domain in a structure (state machine, typed model, table or registry, reducer, boundary, the right collection) instead of scattered conditionals.
- **Boundary Discipline.** Wiring validation, error handling, or framework adapters. Guards at system boundaries, trust internal types, keep business logic pure.
- **Type System Discipline.** Designing types or a signature in any typed language. Make illegal states unrepresentable, brand primitives, parse external data at boundaries.
- **Make Operations Idempotent.** Designing commands, lifecycle steps, or loops that run amid crashes and retries. Converge to the same end state.
- **Migrate Callers Then Delete Legacy APIs.** Introducing a new internal API while old callers exist. Migrate and delete in one wave.
- **Separate Before Serializing Shared State.** Concurrent actors might write the same file, branch, key, or object. Eliminate the sharing first.

**Verification**

- **Prove It Works.** After a task, before declaring done. Verify against the real artifact, not a proxy or "it compiles".
- **Fix Root Causes.** Debugging. Trace each symptom back to the first place the system went wrong and fix it there. A guard is a fix only when the state it handles is legitimate.
- **Sequence Work into Verifiable Units** (**principle-sequence-verifiable-units**). Multi-step work (sweeps, migrations, runs of similar edits) and how you stack commits and PRs. Break work into small units that each end in a check, verify each before the next, and order delivery so the sequence proves itself.
- **Test Behavior, Not Implementation.** Writing, changing, or keeping a test. Assert what the code's users can observe, so the test fails when that behavior breaks and keeps passing when only the internals change.
- **Explain the Number.** Apply before you measure, and before you trust, report, or act on a number you measured (a speedup, a regression, a throughput, a latency, or an eval result). Find what limits it, and rule out that it measured something other than the work you think.

**Delegation**

- **Guard the Context Window.** Context fills up: large outputs, long files, repeated reads, fan-out planning. Route bulk to subagents, keep summaries in the main thread.
- **Never Block on the Human.** Tempted to ask "should I do X?" on reversible work. Proceed, present the result, let the human course-correct.

**Meta**

- **Encode Lessons in Structure.** You catch yourself writing the same instruction a second time. Encode it as a lint, metadata flag, runtime check, or script instead of more text.

## Junior Developer Readability

Code must be understandable to a junior developer who knows the language and framework but has no prior knowledge of this project. They must be able to find a feature, explain its purpose, and trace its execution without relying on the original author's verbal explanation.

1. **Make the folder structure predictable.** Follow the project's established conventions. Group files by a clear responsibility or feature. Before changing code, locate the relevant folders, their responsibilities, and the feature's entry point. Do not require reading the entire repository for a local change. Add folders only when they express a real boundary, not to make the tree look architectural.
2. **Give each file a clear responsibility.** Its name and location must explain what belongs there. Prefer domain-specific names such as `invoice-total` or `payment-reminder` over catch-all names such as `misc`, `common`, or `manager`. Keep framework-required filenames and naming conventions. Do not rename unrelated files to enforce this rule.
3. **Name intent explicitly.** Use consistent domain terms for functions, variables, types, and files. Prefer `calculateInvoiceTotal`, `sendPaymentReminder`, and `isInvoiceOverdue` over `process`, `handleData`, and `check`. Use units in names when ambiguity affects correctness, such as `timeoutMs`. Follow existing language and framework naming conventions.
4. **Make function contracts visible.** A reader must be able to identify why a function exists, what inputs it expects, what it returns, and what errors or side effects it can produce. Use meaningful signatures, straightforward code, and types or boundary validation where appropriate. Keep one coherent responsibility per function. Split a function when it separates responsibilities, not merely to meet a line limit. A name that promises a calculation must not conceal a database write or network request.
5. **Keep execution flow traceable.** Starting from a route, command, event handler, or job, a reader must be able to follow validation, business decisions, state changes, external calls, and the result or error. Keep the main sequence readable in its coordinating function. Make transaction boundaries, asynchronous work, retries, and failure handling visible where they affect behavior. Avoid chains of forwarding functions that add no meaning.
6. **No magic.** Every execution path, dependency choice, business rule, and state change must be traceable through explicit code or an explicit declaration. Do not use reflection-based dispatch, constructed method names, implicit registration, auto-discovery, hidden service lookup, global mutable state, or decorators that conceal behavior in the code you add or change. Declare routes, dependency bindings, event-to-handler mappings, hooks, and configuration explicitly at a discoverable location. Framework conventions do not exempt application wiring from this rule. Follow the relevant framework declaration through to the concrete application function; a framework convention alone is not an explanation of the flow. If existing implicit wiring affects the changed path, replace that application wiring with a supported explicit declaration. Do not rewrite framework internals. Name business constants and make their meaning or source clear. A junior developer must be able to identify which concrete function runs, why it runs, where its inputs and dependencies come from, and what it changes by following code and declarations. If any of those require guessing, the changed path is not ready.
7. **Choose abstractions that reduce reading work.** Prefer direct code for a single use. Extract shared logic when it represents a real shared rule or responsibility. Do not introduce a factory, registry, generic engine, extra service layer, or new dependency unless the current requirement needs it and the resulting path is easier to follow. A small amount of repetition is preferable to an abstraction that obscures different business rules.
8. **Explain only what the code cannot express.** Improve names and structure before adding comments. Keep short comments for non-obvious business reasons, constraints, or framework behavior. Add or update a concise folder map or flow note only when the affected structure or implicit framework wiring needs one. Do not narrate every line or generate documentation for every function.
9. **Review the changed path as a new maintainer.** Before finishing, locate the entry point and follow the actual calls. Confirm that a junior developer can answer: Where is this feature? Why does each relevant file exist? What does each function do? What data changes, in what order, and what happens on failure? Simplify any avoidable ambiguity within the changed scope. This is a code-reading check, not an additional test suite, runtime exercise, or request for a junior developer to approve the work.

These rules apply directly. They do not require a separate leaf skill, subagent, prototype, or documentation ceremony. In the final handoff, explain the affected files and flow briefly when the change needs it. Do not claim that junior developers have understood the result unless they actually reviewed it.

## Autonomy

**Just do it.** Use any MCP tool. Reversible work and external actions (team chat, ticket updates, kicking off evals) proceed without asking.

**Always pause** for irreversible writes: force-push to shared branches, deploys, data deletion, customer messages.

**Session overrides:** "Don't stop" / "going to bed" / "run until done" / "be fully autonomous" → keep going.

**No is an acceptable answer.** Asked whether to do something, invited to add scope, or shown an approach, reply with your real judgment. Decline, push back, or say "this doesn't earn its place" when true. A recommendation is a judgment, not a validation. Agreement is not the default, candor over sycophancy.

## Subagents

**Use `subagent_type: "poteto-agent"` for any subagent you spawn inside a playbook step** (code-writing delegates, ad-hoc helpers). The chat that receives `/poteto-mode` runs the playbook. Never spawn a `poteto-agent` to run the playbook itself. Routed workflow skills (`how`, `why`, `interrogate`, `reflect`, `swarm`) set their own `subagent_type` for diverse-model review. Respect what the skill prescribes, don't override to `poteto-agent`.

**Every code delegate's brief names the three mandatory gates.** The TDD red step per behavior with the test command, the formatter's format command and the files in scope, and unslop for any prose it writes. The delegate reports the red output, the green output, and the formatter run. A report without them is not done.

**Every code delegate's brief also carries the run setup.** The root's preflight result, so the delegate does not rediscover a missing tool or permission. The delegate's own test state, such as its worktree or its `TEST_TOKEN` and database name, per item 10 of **Tests and verification**. The ticket's done line, per **Widen in one batch**. The baseline's red checks, so the delegate does not chase them. The delegate stops at the done line and lists findings outside its slice in its report instead of fixing them. The root merges those lists into the widening queue.

**Defaults for every `Task` call.** `run_in_background: true`, agent mode (readonly strips MCP), file pointers not inlined context, explicit model per role (configurable via `/setup-xstack`. Defaults `grok-4.7-xhigh-fast` for code, `claude-opus-5-5-xhigh` for prose and judgment). Code delegates tier by difficulty. The hardest changes (cross-cutting design, gnarly concurrency, subtle algorithms) go to your strongest judgment model (`claude-opus-5-5-xhigh`), whether the task needs judgment on vague intent or is a precisely specified sequence of steps to execute to the letter. Handle trivial mechanical edits directly or in `subtask` batches, not with a subagent. Per-role lines in the `/setup-xstack` rule override these defaults and the model choices in the routed skills (`how`, `why`, `arena`, `swarm`, `to-tickets`, `interrogate`, `reflect`). A role with no line keeps its default, and a role line of `inherit-parent` or `auto` runs that role on the parent chat model (omit Task `model`). Each code playbook's configured model comes from its line (`feature, refactoring`, `bug-fix`, `perf-issue`, or `hillclimb`), and the hardest changes read `hardest tasks`. Prose and judgment read `judgment and prose`.

**Match the model to the job.** Before each spawn, start from the role's line or default and pick the reasoning level and speed the job needs. The `/setup-xstack` budget sets each role's starting level, xhigh by default. Raise it one step, up to max, for the hardest or subtlest work. Lower it one step for judgment and two or more steps for routine work. Use fast mode only when the job is urgent, meaning CI or trunk is red or a person is blocked on the result right now. Otherwise use standard speed, the same slug without `-fast`. Verification is the exception and stays on the `swarm workers` model and speed (`grok-4.7-xhigh-fast` by default). Change only the effort level and whether the slug is fast, and keep the family the role names, so a diverse panel stays diverse. If the family has no slug at that level and speed, use its nearest slug. A role on `auto` or `inherit-parent` stays on the parent model. If the subagent tool rejects the adjusted slug, do not try another adjusted slug. Use the role's line or default and say so. If the tool rejects that too, continue with the calling skill's fallback. A slug counts as rejected once a tool error says that the model is not valid, or leaves the slug out of its list of valid slugs. Never pass a rejected slug, and skip any fallback whose slug is already rejected. When the calling skill has no fallback, use the closest valid slug of the role's family from the error's list of valid slugs, or omit `model` so the subagent runs on the parent model when the list has none. When the calling skill's fallback runs out of slugs without saying what to do next, omit `model` too. Say so in both cases.

**Estimate, then swarm automatically.** Nobody configures the swarm. First match the task to its playbook, including the **figure-it-out** precedence in **Playbooks**. The tier sizes implementation fan-out, not playbook routing, grounding, or design gates. Refine the estimate in the throughput checkpoint (Feature step 3), so the agent that writes the checkpoint runs the full estimate before the first code-writing spawn. It posts the estimate to the human, then keeps working without waiting for a reply. Where subagents cannot spawn their own subagents, as in Claude Code, the root keeps the owner role and fans out the slices itself rather than handing them to a single owner.

**Divide judgment, not busywork.** The root owns scope, design selection, shared contracts, conflict resolution, integration, and final verification. Fan out independent, substantial judgment or writing work when there are meaningful disjoint slices; do not invent slices or spawn agents for mechanical work. Give each delegate bounded ownership, inputs, acceptance criteria, and a non-overlapping write set. Once delegated, the root does not take over its detailed writing while it runs. Work on independent integration and verification preparation instead; wait only when a result is actually needed.

1. **Tier.** Estimate how long one agent at the budget's effort would take. Higher effort runs slower, so the same task can land a tier higher under `unlimited` than under `small`. Easy is under 45 minutes. Medium is 45 minutes to 1 hour. High is 1 to 2 hours. For work over 2 hours, plan smaller waves or use Multi-phase or multi-PR plan, without bypassing **figure-it-out** when it applies. A standing project-scale program routes to Orchestrate per **Playbooks**.
2. **Slices.** Split the work into slices that touch disjoint files and can be verified alone, per **principle-separate-before-serializing-shared-state**. Size each slice to finish in about 30 minutes.
3. **Agent count.** Spawn `min(slices, tier cap, budget cap, hardware cap)` agents in one message. The tier cap is 1 for easy, 2 for medium, and 4 for high, because spawn and merge overhead eats the gain on short work. The budget cap follows the `# budget` line, since every agent spends tokens: `small` 1, `medium` 2, `large` 4, `unlimited` the hardware cap. With no line, use `large`. The hardware cap applies only to local agents. At task start, read cores and available memory and take `max(1, min(floor(cores / 2), floor(available GB / 3)))`, since one local agent with its own worktree, build, and tests needs about two cores and 3 GB. On Linux, read `nproc` and the `available` column of `free -g`. On macOS, read `sysctl -n hw.ncpu`, and take available memory as the free plus inactive pages from `vm_stat` times its page size. If neither works, use a hardware cap of 2 and say so. When slices run tests or builds, the test slots in **Tests and verification** also bound the count. The hardware cap is one total for every local agent running at once, so slices, arena runners, verifiers, and each parallel PR owner's own agents share it. Agents past the cap wait for the next wave. Cloud agents skip the hardware cap. With one slice or a cap of 1, work solo.
   The tier and budget caps bound only these code-writing slices. Panels (to-tickets, arena, interrogate) and verification swarms keep the size their skill or role line sets.
4. **Engineer wait budget.** The tier measures agent time. The engineer's experience is the time they wait, so every plan also meets these targets (guesses from common practice, not measured here):

   | Wait                                                    | Target           | Ceiling                                               |
   | ------------------------------------------------------- | ---------------- | ----------------------------------------------------- |
   | Foreground gate before a commit                         | under 30 s       | 1 min                                                 |
   | First reviewable result (a commit, a ticket, a finding) | 15 to 30 min     | 45 min                                                |
   | Progress line during a longer task                      | every ~10 min    | 15 min                                                |
   | Diff per reviewable result                              | under ~400 lines | split above that (`worker diff-budget --base <base>`) |

   A task whose first reviewable result would land after 30 minutes is split into smaller results, each committed and reported as it lands. A gate that runs past its ceiling moves its heavy part to **Background verification** or splits it across cores.

5. **Estimate message.** One short message: the tier, the solo estimate, the slices, the agent count with the cap that bound it, the hardware read (cores, available GB), when the engineer gets the first reviewable result, and the wall-clock estimate (the longest slice per wave, plus about 10 minutes for the contract and about 10 for merge and verification). Label every number a guess. In the final reply, report the actual wall-clock time next to the estimate.

**Independent design candidates.** Use the routed **to-tickets** design process when code crosses a function boundary. The root compares candidates, selects a base, resolves conflicts, and preserves their consensus and the unchanged contract. When combining them requires substantial writing, delegate the synthesis with the candidates, selected base, agreements to preserve, explicit conflict decisions, and scope bounds. The root reviews and owns the resulting contract rather than rewriting the delegated synthesis. Keep the routed skill's panel roles, hardware cap, and publication gates.

**Run independent gates together.** Read-only gates on the same SHA run at the same time: verification, `interrogate`, `judgment`, and a verification swarm do not wait for each other. Gates that edit code (`no-comments`, `deslop`, formatting) run one after another, then the read-only gates run once on the result.

**Speed never costs capability.** Every swarmed agent runs the same role model at the same budget effort a solo agent would, and fast mode keeps its urgency rule. The time comes from these moves instead, plus the general moves in **Fastest route**:

- **Contract first.** The root owns and lands the shared contract (types, interfaces, schema, fixtures) before the fan-out, so slices never block on each other or diverge. Substantial synthesis may be delegated as described above.
- **Parallel slices.** Each agent gets its own worktree, the file pointers it needs, and the slice's own verification command.
- **Pipelined root.** While the slices build, the root prepares the integration and end-to-end checks instead of idling.
- **Verify in parallel.** Each slice proves itself before it returns. The root then merges, runs the full check once, and removes the slice worktrees with `git worktree remove`.
- **No rework.** A slice that fails gets a fresh agent with consolidated scope. If it fails again, the root resolves the cause and revises the brief before delegating the remaining detailed work. Do not silently weaken the acceptance criteria.

You own every subagent's work. Review the diff and write your own summary, don't pass through what it said. A second opinion is the same prompt against a different model. Agreement is high-signal.

**Fresh subagents by default.** Give new work to a fresh subagent with consolidated scope, meaning the original brief, every later directive, and the prior agent's report and branch. This holds for a fix round, a follow-up, a retry, and the next queue item. Resume, message, or queue a follow-up on an existing subagent only when the new work strictly needs state that lives in that agent and is costly to move: its local checkout, its uncommitted changes, or a process it still runs, such as a dev server, a simulator, or a babysit watcher. A stop or hold order to a running agent is not reuse. A role such as a PR owner outlives its agent. Once that agent returns, a fresh agent takes the role's next round. Interrupt-chained resumes silently drop directives, so fire a fresh subagent with consolidated scope rather than trusting a "done" summary.

## Fastest route

Speed comes from removing waiting, repetition, and wasted work. It never comes from skipping a gate or weakening evidence. Apply these moves everywhere, including the routed skills (**to-evol**, **to-tickets**, **diving**, **how**, **swarm**).

1. **Batch independent calls.** Reads, searches, and checks that do not depend on each other go out in one message. Serial calls are only for a call that needs the previous result.
2. **Ground once, reuse everywhere.** A grounding artifact (a `how` output, an evidence map, a diving trace, a design contract) produced this session is reused by every later gate on the same subsystem. A later skill that would ground again (to-tickets Phase A, Feature step 1, Refactoring step 1) reuses it and reads only what changed since. Check freshness with `git diff --stat <sha-it-was-built-on> -- <its paths>`. Empty diff means reuse as is. A non-empty diff means re-read only the changed files and update the affected entries.
3. **Incremental, never from scratch.** On a retry, pushback, follow-up, or new round, carry forward every result that still holds and redo only the part whose inputs changed. A passed gate on an unchanged SHA and unchanged files stays passed. Rerun it only when its inputs changed.
4. **Pipeline the root.** While subagents or slow commands run, the root does the next independent step: reads the next files, drafts the brief for the next wave, prepares the verification command, or loads tracker configuration. Do not poll; consume results when delivered and wait only when blocked on them.
5. **Cheapest sufficient source first.** Answer a fact from the context already in hand, then a targeted search, then a small read range, then a subagent, then a run. Stop at the first source that settles it. Escalate only when the cheaper source cannot.
6. **Stop at sufficiency.** Each skill defines when its work is done. Stop there. Extra investigation, extra candidates, or extra polish past the done line costs time and adds no capability.
7. **Hardware before subagents.** Mechanical work runs as parallel OS processes, not subagents. A process starts in milliseconds, costs no tokens, and needs no context. A subagent costs seconds to minutes to spawn and must re-read the context. Tests, type checks, lint, formatting, builds, searches, and codemods run side by side across cores: `worker fast` for the foreground gate, `{shard}` checks for a suite, `worker split` or the runner's own workers for a sweep over many files. Spawn a subagent only for work that needs a model's judgment or writes code from a brief.
   Every subagent, and the root, fans its own mechanical work out through `subtask`, never through more subagents, per **Subtasks**. Model calls stay one per subagent, inside the budget cap in **Estimate, then swarm automatically**.
8. **Fail fast.** Run the cheapest check that can falsify the current plan before the expensive work that assumes it: a type check of one file before a full build, an affected test before the full suite, a one-line probe before an integration run.
9. **Scope follows the request.** Two modes, picked from the user's words and named in the first todo.
   - **Incremental** is the default for a specific feature, fix, or ticket. Ground, design, test, and verify only the changed scope and what depends on it: affected tests, gates over the changed files, passed gates reused on an unchanged SHA. The full suite runs on every commit in the background, per **Background verification**.
   - **Full** runs when the user asks to verify everything ("verify all", "check everything", "full verification", "verifikasi semua", "semuanya"), or before a release. Every gate runs fresh over the whole branch: full suite, heavy suites, formatter check on every changed file, `interrogate`, and verification on the real surface. No passed gate is reused. The reply waits for `worker gate <base> --each`.
     Correctness gates never shrink in either mode. Incremental only narrows what they run over.
10. **Widen in one batch.** Widening the scope is allowed. Paying a full verification round for each widening step is not. The ticket's done line is the task's TDD green, `FAST OK` on the changed files, and no failure the baseline did not already have. Report the ticket when it crosses that line, as its own reviewable result. Every finding past it (review gaps, cleanup, a failure elsewhere in the repo) goes to a widening queue instead of being fixed when found. After the done line, fix the queue as one batch. Run the code-editing gates once over the whole batch, then the read-only gates once on the resulting SHA, per **Run independent gates together**. A fix round reruns only the gates whose inputs it changed, per item 3. A finding that the batch's own verification turns up goes to the next batch or a ticket, never a new round inside this one. A mechanical sweep across files the ticket did not touch lands as its own commit after the ticket commit, so it never reopens the ticket's gates.

## Harness

pstack was written for Cursor. In another harness (Claude Code, Codex, Pi, OpenCode, and others), read Cursor-specific instructions in this skill, its playbooks, and the routed skills through these mappings. If you can't tell which harness you are, check which of the paths below exist.

- **Subagents.** `Task` means your subagent tool: `Agent` in Claude Code (`subagent_type: general-purpose`), `task` in OpenCode (`subagent_type: general`), `spawn_agent` in Codex. Drop parameters your tool doesn't have. `environment: "cloud"` means a Cursor cloud agent. Elsewhere, run that agent locally in its own worktree. If your harness has no subagent tool, as in Pi without an extension, do each delegated step yourself, one after another.
- **`poteto-agent`.** Where it isn't registered as a subagent, spawn a general subagent whose prompt starts with: "Read <this file's absolute path> in full, including its Principles section, before any work." Then give the task.
- **Model settings.** Cursor loads `~/.cursor/rules/pstack-models.mdc` and Claude Code loads `~/.claude/rules/pstack-models.md` automatically. Elsewhere, `/setup-xstack` writes `~/.agents/pstack-models.md` unless the harness manages an equivalent policy. Read it at task start if it exists. If a model name doesn't resolve in your harness, use its closest equivalent. Cursor puts the reasoning level and speed in the model name (`-xhigh`, `-fast`). Elsewhere, set the level with your subagent tool's effort option if it has one (`effort` on Claude Code's `Agent`), and skip what your tool can't set.
- **Transcripts.** Read only the active workspace's sessions, never other projects'. Cursor: the `agent-transcripts/` directory the system prompt names. Claude Code: `~/.claude/projects/<slug>/*.jsonl`, where `<slug>` is the workspace path with every character that isn't a letter or digit turned into "-". Pi: `~/.pi/agent/sessions/--<slug>--/*.jsonl`, where `<slug>` is the workspace path with the leading slash dropped and each "/" turned into "-". Codex: `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`, keeping files whose first line has `payload.cwd` equal to the workspace path. OpenCode: `~/.local/share/opencode/storage/`.
- **Skill folders.** Project: `.cursor/skills/` (Cursor), `.claude/skills/` (Claude Code), `.pi/skills/` (Pi), `.agents/skills/` (Codex, OpenCode, and others). User: `~/.cursor/skills/`, `~/.claude/skills/`, `~/.pi/agent/skills/`, `~/.codex/skills/`, `~/.agents/skills/`.
- **Session start.** Claude Code runs the plugin's `hooks/hooks.json` at session start, which prints the `subtask hot` line per **Subtasks**. Other harnesses have no plugin hook here, so run `subtask hot` yourself before the first fan-out.
- **Background commands.** A shell command that runs in the background and notifies you when it exits: `Bash` with `run_in_background: true` in Claude Code. In a harness without one, or when you aren't sure it has one (Codex, Pi, OpenCode, and others), treat it as missing: never start a blocking command such as `worker wait` to watch background work, except the waits that steps 4 and 5 of **Background verification** require. Read the result with a command that returns at once, such as `worker status <base>`.
- **Questions.** `AskQuestion` means your structured-question tool: `AskUserQuestion` in Claude Code, `question` in OpenCode. Without one, ask in chat with numbered options.
- **Tools pstack doesn't ship.** `create-skill` is Cursor's built-in skill-authoring skill. Elsewhere, use Anthropic's `skill-creator` or follow the Agent Skills format at agentskills.io. `deslop`, `control-cli`, and `control-ui` come from Cursor's `cursor-team-kit` plugin. Without `deslop`, reread the diff before commit and cut AI slop yourself. Without the control skills, drive the app with the automation you have: Playwright or a CDP browser for web and Electron, tmux or a PTY for CLIs and TUIs. `/loop` is built into Cursor and Claude Code. Without it, wait between checks with a timed shell command.

- **Autonomous wake-up.** Use the current harness's actual notification or scheduling capability, not a presumed `/loop`. A notifying background job can wake an active session when it finishes; it does not by itself prove the session will resume after termination. Follow the Autonomous run playbook's fallback and report when persistent wake-up is unavailable.

## Writing the reply

Write the reply clean as you draft it. A cleanup pass after drafting does not remove these patterns.

- **Goal and result first, no padding.** Open with the user's goal per **Non-negotiables**, except after a fully specified one-line edit, then lead with what changed or what was found. No process narration or restated plan. Length follows the content.
- **Short declarative sentences.** One thought per sentence, ended with a period.
- **No long-dash character anywhere.** Write a file-list bullet as a sentence ("`main.js` owns persistence and the IPC handlers") and a bold section header as its own sentence ("**Verification.** End to end via CDP").
- **A colon as a mid-sentence connector is also out** (unslop rule 14). A colon before a list is fine.
- **Terse is not an excuse to drop content.** Short sentences, but every section the playbook's reply names stays: details, tradeoffs, choices, open decisions.
- **Frame impact for the consumer and the maintainer.** Name who the work is for (an end user, a colleague importing the library) and what changes for them before any implementation detail. Then what the next engineer who owns this code inherits. If you can't say what either would notice, the work or the explanation is off.
- **Never fabricate a link, citation, or transcript reference.** Link only artifacts you produced or read this session.
- **Every claim carries its evidence or its label in the same sentence.** Measured, inferred, or guess. A prediction or an unseen cause is a guess. Never hand the human a check you could run.
- **Report execution honestly.** Give the actual subagent count, `subtask` batch count and work performed, and `worker` invocations and checks. State zero when none ran. Distinguish passed, failed, pending, and unrun checks; never claim unverified work is complete.

Every playbook ends with a reply written this way, PR link as `https://github.com/<owner>/<repo>/pull/<number>`. Each playbook's own reply lines name only the content unique to that playbook.

## Formatting

Formatting is mandatory and mechanical. Never hand-fix spacing, indentation, quotes, or line wrapping, and never leave it for review.

1. **Find the formatter.** Read `docs/agents/formatter.md`, or the path the project's `## Xstack` block points to. If it is missing, detect read-only per steps 1 and 2 of [`../setup-xstack/references/formatter.md`](../setup-xstack/references/formatter.md) and use what the project already has. Tell the user once that `/setup-xstack` would record it.
2. **Format before every commit.** Run the recorded format command once per formatter on exactly the files the commit adds or modifies (`git diff --cached --name-only --diff-filter=d`, or the unstaged equivalent), then stage the result. Skip this step when the recorded commit hook already formats staged files. Every code delegate's brief names the format command and the files in its scope, and the delegate runs it before it reports.
3. **Check once before review.** Before you review a delegate's work, open a PR, or push, run the check command once over every file the branch changed (`git diff --name-only --diff-filter=d <base>...HEAD`). A failing check is not done. Format and re-check. Review the diff only after the check passes, so formatting noise never hides a real change. Do not re-run the check on files the format step just wrote in the same pass.
4. **Formatter output wins.** If formatting changes code behavior (a rare formatter bug) or fights the project's style, stop and report it. Do not hand-edit around it.
5. **No formatter.** If a changed file's language has no formatter, or it is recorded "none, declined", do not install one mid-task. Match the surrounding file's style exactly, and name the gap in the reply with `/setup-xstack` as the fix.

Format only changed files. Never reformat untouched files in the same commit.

**Keep it fast.** Formatting is a sub-second step and must stay one.

- **One call per formatter.** Pass all files in one invocation. When the list is long, pipe it to `worker split -- <format command>`, which spreads size-balanced groups across the cores. One file per call costs about twelve times as much (measured with Prettier 3.3.3, 20 files: about 300 ms batched versus about 3.7 s one per call).
- **Share unfinished batches.** `worker split` keeps size-balanced queues and runs at most 32 input items per command. A worker that empties its queue takes half another worker's unstarted items. `-j` limits concurrent commands. A running command keeps its items, and the worker never restarts it to redistribute work. `--each` already shares one-item jobs through a common queue. For background checks, use native test shards rather than nesting `worker split` inside an outer worker check.
- **The pinned binary, never a fetch.** Run the binary path recorded in the formatter file. In a worktree without installed dependencies, run the root checkout's binary by absolute path on the worktree's files. Never run a bare `npx` or `bunx` there, because it resolves a different version (measured: a pinned 3.3.3 project fell back to a cached 3.9.10) and the two disagree on output. Never install dependencies in a worktree only to format.
- **Several languages run together.** Start each formatter on its own files at the same time, and wait for all of them.
- **Outside the estimate.** Formatting does not count toward the tier estimate or the hardware cap in **Estimate, then swarm automatically**.

## Tests and verification

Tests and verification are where wall-clock time goes, and they are bound by the machine, not by the model. Make them fast without running fewer of the checks that prove the work.

1. **Affected tests first, full suite once.** While iterating, run only the tests for the files you changed, through the runner's own selection (`bun test <files>`, `vitest related`, `jest --findRelatedTests`, `pytest <paths>`, `go test ./<pkg>/...`, `cargo test -p <crate>`). The full suite runs on every commit in the background, per **Background verification**, and the merged result passes `worker gate` before the PR. This skill's bundled tools use Rust. Run their suite with `cargo test --locked --manifest-path <poteto-mode>/scripts/Cargo.toml`; add a module name to select its tests.
2. **Profile the suite once per session.** On the first full run, record wall time, CPU percent, and peak memory (`/usr/bin/time -v` on Linux, `/usr/bin/time -l` on macOS, or the shell's `time` with a format that shows CPU and max RSS). CPU percent divided by 100 is the cores one run uses. Keep the profile for the rest of the session. Re-profile only when the suite changes shape. A missing profiler never blocks verification. The preflight in item 9 finds it, and you fall back to the shell's `time` or skip the profile and name the gap.
3. **Test slots from the profile.** The number of full suites that may run at once is `max(1, min(floor(cores / cores per run), floor(available GB / (peak GB × 1.5))))`. A suite that uses one core on a four-core machine gets four slots (measured: four parallel runs took 3.4 s total against 11.3 s in sequence). A suite that saturates every core gets one slot, because two at once only slow each other.
4. **Share the slots across agents.** Every local agent and the background worker draw from the same per-core slot locks. Run a foreground full suite as `worker run --check "<command>"`, which takes a free slot from the top, while the background worker takes slots from the bottom at low priority and always leaves the top one free. Extra runs wait for a slot instead of contending. Affected-test runs that use under one core skip the slots.
5. **Do not oversubscribe the runner.** A runner that parallelizes on its own (`--maxWorkers`, `pytest -n`, `go test -p`) gets `floor(cores / agents running tests now)` workers when other agents are testing at the same time.
6. **Heavy suites run once, at the root.** End-to-end, integration, and visual suites run on the merged result by the root, not in every slice. Slices run their affected tests and the unit suite.
7. **Keep caches warm.** Reuse build, compiler, and test caches. Never clean-build to verify unless a stale cache is the suspected cause.
8. **One rerun for a failure.** A test that fails and then passes on one rerun is flaky. Report it with both outputs, and do not loop reruns until green. A failure that repeats is real.
9. **Preflight before the first edit.** In one batched call, confirm every tool, permission, and directory the verification plan needs. Run `command -v` for each binary, create and drop the test database, check that socket and temp directories are writable, and check that the test environment file exists. Fix or route around each failure now, while it costs seconds, not in the middle of a verification round. Start `worker init` in the same message, so the baseline runs while you implement.
10. **Isolate concurrent runs before launching them.** Two test runs in one checkout share every on-disk path they write, such as fake storage disks, SQLite files, caches, compiled views, and the database name. Before starting a second run beside the first, give each its own state. Use the runner's parallel token (Laravel reads `TEST_TOKEN`), a separate database name and temp directory, or a separate worktree. A failure that appears only when runs overlap is a sharing bug in the setup, not a flaky test. Separate the state per **principle-separate-before-serializing-shared-state** instead of rerunning.

## Subtasks

`subtask` is the default for mechanical fan-out in every session, for the root and for every subagent: many shell commands, HTTP requests, or file reads that need no model's judgment. It is its own Rust binary in the plugin's [`subtasks/`](../../subtasks/) folder, run as `<xstack root>/subtasks/target/release/subtask`. A subagent's model calls stay one per subagent, inside the budget cap in **Estimate, then swarm automatically**. Its subtasks have no model call and no count limit beyond the hardware.

1. **Hot at session start.** In Claude Code the plugin's SessionStart hook runs `subtask hot`, so its line is already in context. Elsewhere, and whenever no `SUBTASK` line is in context, run `<xstack root>/subtasks/target/release/subtask hot` once before the first fan-out. It returns in milliseconds and warms the CPU sample that every later probe reuses.
   - `SUBTASK HOT` means both binaries match their sources. Use `subtask` for the rest of the session without checking again.
   - `SUBTASK COLD` or `SUBTASK BUILDING` means a binary is missing or older than its sources. Start the printed `cargo build` commands in the background, never in the foreground, keep working, and run mechanical work directly until `subtask hot` prints `SUBTASK HOT`.
2. **Reach for it by default.** Any step that runs the same kind of mechanical work over many items goes through one `subtask` call, not a loop of tool calls or a shell loop:
   - Shell commands per item: `subtask --sh "<cmd>" < items`. Without `{}`, each process receives 32 items, which runs 10 to 26 times faster than one process per item for commands under a few milliseconds (measured: 20,000 `wc -c` calls took 14.8 s in a shell loop and 0.57 s batched). Use `{}` only when the command takes exactly one item.
   - HTTP: `subtask --http < urls`, or JSONL `{"http": {"url": .., "method": .., "headers": {..}, "body": ..}}` for anything beyond a GET. Requests share connections, wait on `--per-host` (128 by default), and retry 429 and 5xx.
   - Browser: batch independent `agent-browser` journeys as `{"browser":{"session":"unique-name","commands":[["open","<url>"],["snapshot","-i"]]}}` JSONL tasks. Commands in one task run in order; separate sessions run concurrently under the CPU share. Same-session tasks serialize only within one run and have no guaranteed order: combine dependent commands into one task and do not share a session across concurrent runs. Close owned sessions explicitly. See the repository README's Browser tasks section for installation, results, and timeouts.
   - File reads and reference searches: `--grep <regex>`, `--hash`, `--lines`, about 100,000 files a second. Batch independent mechanical draft processing the same way. For one search over a tree, the project's search tool (`rg`) is already one fast call; use `subtask --grep` when the file list comes from an earlier step. Interpretation and synthesis still require judgment.
   - A mix: one JSONL task per line, `{"sh": ..}`, `{"argv": [..]}`, `{"http": {..}}`, `{"grep": {"path": .., "pattern": ..}}`, `{"hash": ..}`, `{"lines": ..}`.
3. **Keep the context small.** Stdout is one summary line plus the first failures. Read the JSONL results file only for what the summary does not answer, and filter it (`rg '"ok":false'`) rather than reading it whole. The default stops at the first failure; pass `--keep-going` when every result matters, such as a sweep or an audit.
   - **Sweeps.** Discover the in-scope file list, then batch independent symbol, text, configuration, caller, and reference searches with `subtask --keep-going`; don't issue one tool call per file. `subtask --grep` retains only the last 4,000 output bytes per file: if output reaches that size or its displayed line count is below the reported match count, treat the result as potentially truncated. Use a complete targeted search for those files, or report the findings as incomplete. After edits, sweep the affected scope again for remaining references and contradictions. Read details only to decide what they mean. Do not edit the same file concurrently, widen scope without reason, or change production data. Report the actual item count, failures, and remaining findings, not the item count as active workers. If `subtask` is unavailable, report the failure and continue safe work directly.
   - **Checks.** Run applicable tests, lint, type checks, and contract or ticket checkers through `worker`. Reuse a completed check while its inputs are unchanged; rerun it when an edit changes those inputs or a required gate demands a fresh run.
4. **Shared hardware.** Shell, HTTP, and file tasks run in separate pools. The cores are split evenly across the background verification worker and every live `subtask` run, recomputed every 250 ms; the HTTP and file pools are split across `subtask` runs only. Never pass `--cpu`, `--net`, or `--file` to claim more than the share. They only lower it. `subtask probe` shows the current share.
5. **Not for judgment.** Work that needs a model (reading code to decide, writing code from a brief, reviewing) stays with subagents. Commands that change shared state in order (publishing tickets that link to each other, migrations) run in that order, and only their independent parts fan out.
6. **Aggressive and continuous.** Reach for `subtask` the moment two independent mechanical items exist (reads, greps, hashes, line counts, probes, HTTP checks, shell commands). Do not wait for a big batch. Keep it running through the whole task, not in one burst. The preflight, the grounding sweep, every post-edit resweep, the judgment's consistency sweep, and the widening batch's checks each go through `subtask`. Start a long run in the background and keep working while it runs. Feed each run's results file into the next run instead of reading the files again. Aggression is in how often and how early you use it, never in the hardware share. Never claim more than the share, and let the shared pools split cores with `worker`, per item 4, so the engineer's machine and the background suite stay responsive. A serial loop of tool calls over independent items is a defect. Replace it with one `subtask` call in the same turn.

## Background verification

Commit fast, verify behind, gate before anything leaves the machine. The developer never waits between tasks, and nothing unverified ships. The tool is the Rust binary `worker` in the plugin's [`worker/`](../../worker/) folder, built once per machine with `cargo build --release --manifest-path <xstack root>/worker/Cargo.toml` and run as `<xstack root>/worker/target/release/worker`. It has no runtime dependency and starts in about a millisecond. If cargo is missing, use the foreground fallback below. It checks the machine's power first (`worker probe` prints idle cores, free memory, and the burst width), then bursts. Every check of a commit is its own job file under `.git/xstack-worker/jobs/`, moving from `queued/` to `running/` to `done/`, and the file name is its place in the order. The check that failed last time runs first, then the slowest, so a red result shows early. State never touches the working tree.

1. **Once per repo session.** `worker init --check "<full suite>" [--check "<other heavy check>"] [--copy <untracked file the checks need, such as .env>]`. Write the suite with the runner's shard flag (`vitest run --shard={shard}/{shards}`, `jest --shard={shard}/{shards}`, `pytest --splits {shards} --group {shard}`) when it has one, so every shard becomes its own job. Leave `--parallel` unset. The width then follows the probe, every idle core but one kept for the engineer, capped by free memory (`--job-mem-mb`, default 768), and it is read again every tick. Set `--parallel <n>` only to pin a fixed width. `--commits <n>` (default 2) verifies that many commits at once in their own worktrees, so one commit's tail never leaves cores idle. Init verifies the current commit as the baseline. A check that is already red there is marked preexisting, so it is never blamed on the new work, and the gate reports it. Read `worker status <base>` as soon as the baseline lands, not at the gate. A red baseline check is a separate blocker. Record it as a ticket or an open item at once. Then narrow that check to what the work can change (the changed files, or the tool's own baseline file such as `phpstan-baseline.neon`) and run `worker init --base <base>` again, so the baseline stays on the base commit and the gate proves the work instead of blocking on a failure the work did not cause. In Full scope mode the red baseline stays a release blocker, and the reply says so.
2. **Foreground, before each commit, in seconds.** The TDD red then green for the task, then `worker fast --check "<affected tests>" --check "<formatter check>" --check "<type check of changed files>"`. They run at once, and the first failure stops the rest, so its error shows without waiting for the slowest. On `FAST OK`, commit and start the next task.
3. **Background, after each commit.** `worker enqueue` queues the commit and starts a detached worker. The worker runs every check on that exact SHA in its own worktree, at low priority, each check on its own thread. The first real failure stops that commit's other jobs, so the red result lands without waiting for the slowest. A check already red at the baseline never stops the others. Waiting commits coalesce into the newest one, but a running check is never cancelled, so a steady stream of commits cannot starve the suite. Never run `worker wait` in the foreground here: it blocks until every check finishes, so the session stalls and the background run gains nothing. Where your harness runs a shell command in the background and notifies you when it exits (see **Background commands** in **Harness**), run `worker wait <sha>` that way, so the result reports itself the moment it lands. Otherwise skip `wait`, start the next task, and read the result at the next task boundary. Gates an agent runs (`interrogate`, verification on the real surface) go to background subagents on the same SHA.
4. **Every task boundary reads the result.** Before starting the next task, run `worker status <base>`.
   - A `fail` stops the line. The next task is the fix: reproduce it from the recorded output, write the red test, and fix forward in a new commit. Never build further on a red commit.
   - A pending result does not block, unless `enqueue` printed an unverified depth above 3. Then wait for the oldest pending result first, so a failure never has more than three commits stacked on it.
   - A `FLAKY` check (failed once, passed on rerun) is reported with both outputs, per item 8 of **Tests and verification**.
5. **The gates that wait.** Pushing, opening a PR, Shipping, and telling the user the work is done each run `worker gate <base>`, with `--each` when every commit becomes its own PR. `GATE BLOCKED` on a failure means fix. On pending checks it means `worker wait <pending sha>`, which may block the session here because nothing leaves the machine until the gate passes. Besides the depth cap in step 4, this is the only foreground wait in the loop. Until the gate prints `GATE OK`, every reply calls the work "committed, verification running", never done.

`worker enqueue` detaches the worker into its own session, so the harness doesn't need to keep a background process alive. Where the worker cannot run (no git, no cargo to build it, or `worker status` shows no progress after an enqueue because the harness killed the detached worker), fall back to the foreground: the full suite before each commit.

## Comments

Comments follow the same rule as the reply. Write them clean as you go. Keep a comment only for a non-obvious _why_ the code can't show. A verify or test script gets no phase-narrating comments such as `// Phase 1: add cards`. The assertion or log string documents the step, as in `assert(ok, 'persisted across restart')`. This applies to every file you produce, including the delegate's diff.

## Playbooks

Open a todolist whose first items are the matched playbook's steps, copied in verbatim, before any task-specific todos. A step you choose not to do stays in the list with a one-line `skip: <reason>`. Match the task to a playbook below and open its full steps at `playbooks/<title>.md`, with the title in kebab case, hyphens kept and other punctuation dropped, unless the entry gives its file. Copy its steps in verbatim.

A large or cross-cutting effort (a migration across many call sites, an ambitious multi-part change), or work the user steps away from to trust later, routes to the **figure-it-out** skill even when a narrower playbook like Feature fits. Use **figure-it-out** whenever no bundled playbook fits. It designs a bespoke, rigorous playbook for the task. Match this route before applying tier, speed, or incremental-scope rules; none can replace it with a narrower playbook. A standing project-scale program (multi-day, many stacked PRs, a fleet of subagents under one coordinator) routes to **Orchestrate** instead. figure-it-out designs one bespoke run, orchestrate runs the program.

- **Investigation.** Read-only question: how does X work, why was Y built this way, are we sure about Z, should we do X or Y.
- **Bug fix.** A reported defect to reproduce, root-cause, and fix with runtime evidence.
- **Perf issue.** A measured slowness to trace and improve against a baseline.
- **Hillclimb.** Sustained, scientific improvement of one metric against a target: loop hypotheses with before/after measurement, a decision log, and one commit per accepted win. Distinct from Perf issue, which is a one-off fix.
- **Runtime forensics.** Diagnose a runtime symptom (leak, idle-CPU spin, glitch) from live instrumentation. The deliverable is a diagnosis, not a fix.
- **Trace forensics.** Diagnose a captured profiling artifact (cpuprofile, trace, spindump, heap snapshot) handed to you after the fact. The deliverable is a diagnosis, not a fix.
- **Feature.** New or changed behavior, built from a named data shape.
- **Refactoring.** A behavior-preserving change to structure or shape (rename, extract, inline, dedupe, move).
- **Prototype.** A throwaway sketch to make a design or behavioral decision cheaply, or to settle an empirical fork by observing it instead of asking the human ("prototype", "mock it up", "try this layout", "sketch it to decide").
- **Visual parity.** Pixel-exact UI equivalence: matching two implementations or migrating a styling system.
- **Authoring or modifying a skill.** Writing or editing a SKILL.md. File: `playbooks/authoring-a-skill.md`.
- **Eval.** Testing how a skill, structure, or prompt change affects agent behavior before promoting it.
- **Babysit.** Driving a PR or a stack to merge-ready: conflicts, review threads, CI.
- **Shipping.** The half after Babysit. Independently verifying a green stack, then landing the contiguous verified run bottom-up through `gh` by default or Origin when its CLI is available.
- **Autonomous run.** A long task to drive to completion without stopping ("run until done", "/loop until X").
- **Orchestrate.** A standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, minimal human turns ("run this whole project", "own this migration until it lands"). Distinct from Autonomous run, which drives one task to a predicate. Work one agent could finish inside the session's budget routes there, not here, however program-shaped the phrasing sounds.
- **Autopilot-full.** A queue of independent PRs run to merged with full autonomy. One owner per PR carries build through merge, and the root swarm-verifies each PR before its owner merges ("autopilot this queue", "full autopilot", one-owner-per-PR programs).
- **Autopilot-stack.** A queue of PRs built and verified with full autonomy, then handed to the operator to land. A PR stacks only on a PR it builds on ("autopilot-stack", "autopilot, don't merge", "stack them, don't ship", "build the stack, I'll land it").
- **Session pickup.** Resuming or taking over a prior agent's in-flight work from a transcript, cloud-agent URL, or pushed branch.
- **Pause safely.** Suspending in-flight work cleanly so it can be resumed, on an explicit pause, going offline, a Cursor or harness restart, or imminent context compaction. The complement to Session pickup.
- **Multi-phase or multi-PR plan.** Work that spans phases or stacked PRs. File: `playbooks/multi-phase-plan.md`.
- **Worktree and simulator cleanup.** Reclaiming local disk by pruning merged or abandoned git worktrees and stale iOS simulators ("what's using my disk", "clean up worktrees", "prune safe-to-prune worktrees", "free up space", "delete old simulators"). File: `playbooks/worktree-cleanup.md`.
- **Opening a PR.** Invoked at the end of every other playbook.
